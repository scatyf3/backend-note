## 一句话结论

一个操作跨多个服务或多个数据库，还要「要么全成，要么全不成」，是分布式系统里最难的问题之一。**2PC** 能提供原子性，但会阻塞，协调者是单点，性能差，跨服务几乎没人用。实践中的主流是 **Saga**：==把大事务拆成一串本地事务，每一步都配一个补偿操作，失败时按相反的顺序执行补偿==；或者 **TCC**（Try 预留资源、Confirm 确认、Cancel 释放）。它们都放弃了隔离性：中间状态对外可见。所以要靠 outbox 可靠地推进步骤、靠幂等容忍重试、靠语义锁和状态机来缓解隔离问题。

## 为什么本地事务的保证到不了跨服务

单个数据库的事务靠 WAL 和锁实现 ACID（见[索引、事务与隔离级别](/backend/sql-index-transaction)）。一旦「下单」需要同时修改订单库、库存服务、支付服务：

- 它们是不同的进程、不同的数据库，没有共享的事务管理器；
- 任何一步都可能失败、超时，或者结果未知（见[幂等](/backend/idempotency)）；
- 网络分区时，各方甚至没法确认彼此的状态。

## 2PC：两阶段提交

**协调者**分两步驱动所有参与者：

1. **准备阶段**：问每个参与者「你能提交吗？」，参与者把变更写好、加锁，回答 yes 或 no。
2. **提交阶段**：全部 yes 就发提交，否则发回滚。

问题：

- **阻塞**：参与者回答 yes 之后，就进入「不确定」状态，必须持有锁等待协调者的决定。如果这时协调者崩溃，参与者既不能提交也不能回滚，**锁会一直挂着**，直到协调者恢复。
- **协调者是单点**。
- **性能**：多轮网络往返，锁的持有时间被拉长。
- **支持度**：绝大多数消息系统、外部 API、SaaS 服务都不支持 XA。

一个重要的细节：**分布式数据库内部其实在大量使用 2PC**（Spanner、CockroachDB、TiDB 的跨分片事务）。它们之所以可行，是因为每个参与者和协调者本身都是一个通过 Raft / Paxos 复制的组，单台机器宕机不会让「协调者消失」，阻塞的问题就被共识化解了。==所以「不要用 2PC」说的是不要跨服务、跨异构系统用，而不是 2PC 本身不可用==。

## Saga：一串本地事务 + 补偿

把「下单」拆成一个序列，每一步是一个服务内的本地事务，配一个**补偿操作**：

| 步骤 | 操作 | 补偿 |
|---|---|---|
| T1 | 创建订单（status = PENDING） | 取消订单 |
| T2 | 预留库存 | 释放库存 |
| T3 | 扣款（**关键点**） | 退款 |
| T4 | 创建物流单 | 需要的话取消 |
| T5 | 订单状态改为 CONFIRMED | |

T3 失败，就依次执行 C2（释放库存）、C1（取消订单）。

### 设计要点

- **补偿是语义上的撤销，不是回滚**：已经发出去的邮件收不回来，补偿只能是再发一封更正邮件；已经扣的款，补偿是退款，账上会留下两条记录。
- **补偿必须可以重试，并且幂等**：补偿本身也可能失败，要一直重试直到成功。
- **关键点（pivot）**：一旦越过某一步（通常是扣款），就不再回滚，而是**一直向前重试**，直到后续步骤完成。所以关键点之后的步骤，要设计成「最终一定能成功」的。
- **可靠地推进**：每一步完成后，要可靠地触发下一步。靠 [Outbox](/backend/outbox-event-driven) 发事件（编排），或者用工作流引擎显式驱动（协调，见[工作流与 durable execution](/backend/durable-execution)）。

### 编排还是协调

- **编排**（choreography）：每个服务监听上一步的事件、执行自己的事务、再发出事件。没有中心，但流程散落在各处，补偿链很难看清和测试。
- **协调**（orchestration）：一个协调者（工作流）按顺序调用各服务，失败时按顺序调用补偿。流程集中、可见，便于处理超时和补偿，步骤多时更推荐。

### 隔离性的缺失

Saga 没有隔离性：T2 已经扣了库存、T3 还没扣款的时候，别人看到的库存已经减少了；如果后来补偿了，那段时间里别人看到的就是一个「从来没有真正发生过」的状态。缓解办法：

- **语义锁**：用状态字段标记「进行中」（订单 PENDING），其他操作看到这个状态就等待或者跳过；
- **可交换的更新**：设计成先后顺序不影响结果的操作（加减计数）；
- **重新读取再决定**：执行关键步骤前，再读一次最新状态；
- **版本号**：乐观锁防止覆盖别人的更新。

## TCC：Try / Confirm / Cancel

TCC 把每个参与者的操作拆成三个接口：

- **Try**：检查并**预留**资源（冻结 100 元、锁定 1 件库存），带一个过期时间；
- **Confirm**：真正使用预留的资源；
- **Cancel**：释放预留。

所有 Try 都成功，就调用所有 Confirm；有一个失败，就调用所有 Cancel。和 Saga 相比，TCC 的中间状态是「被冻结」而不是「已经生效」，隔离性更好，但每个服务都要实现三个接口，侵入性更强。

TCC 有三个经典的坑：

1. **幂等**：Confirm 和 Cancel 都可能被重试，必须幂等。
2. **空回滚**：Try 因为超时根本没执行（或者没到达），却收到了 Cancel。Cancel 要能识别出「没有对应的 Try」，直接返回成功。
3. **悬挂**：Cancel 先到并执行了，迟到的 Try 才到达，又把资源冻结了，而且再也不会有人释放。Try 执行前要检查这个事务是否已经被取消。

三个坑的共同解法是：每个参与者维护一张事务状态表，记录每个全局事务 id 在本服务的状态。

### 实战：LLMGateway 的预算，就是一个没做 Try 的 TCC

LLMGateway 的流程是：请求前检查预算（`check_budget` 只读不扣），请求完成后再记账。结果是并发请求都能通过检查，预算会被超支一点（README：每个并发请求最多多超一个请求的费用）。README 里也写出了另一种选择：「**请求前预留估算的成本，能让预算变成硬上限，代价是多一次 Redis 往返**。」这正是 TCC 的思路：

- **Try**：按估算的 token 数预留成本（冻结额度）；
- **Confirm**：请求完成后，按实际 usage 结算，多退少补；
- **Cancel**：请求失败，释放预留。

同样要处理 TCC 的那几个坑：请求超时了，预留要能自动过期（相当于 Cancel）；结算可能重试，要幂等。网关选择了更简单的软上限，用一点超支换取热路径上少一次往返，这是一个合理的工程取舍。

## AI 场景：agent 的多步操作就是 Saga

让 agent「订一张机票、一间酒店、一辆车」，本质上就是一个 Saga：

- 每个预订是一个工具调用（一个本地事务）；
- 酒店订不上时，要取消已经订好的机票，也就是补偿。**补偿操作也要作为工具提供**，并且要幂等。
- **关键点要人来把关**：付款这种越过就回不了头的步骤，之前加一个人工审批（见[长任务与 human-in-the-loop](/ai/long-running-agents)）。
- **补偿逻辑最好不要完全交给模型临场发挥**：模型可能忘记补偿，或者补偿错了对象。把补偿链写成确定性的工作流代码，模型负责决策（订哪个航班），代码负责保证「失败了一定会回滚」。

DocPilot 目前的写操作只有 `create_page`，在一个本地事务里写入文档和 chunk，不涉及分布式事务。如果以后加上「把页面同步到外部 wiki」这种跨系统的操作，就要按 outbox 加补偿的方式来设计。

## 追问

::: details 为什么跨服务一般不用 2PC？分布式数据库为什么又在用？
跨服务的 2PC：参与者准备之后要持有锁等待协调者，协调者崩溃会导致无限期阻塞；协调者是单点；多轮往返性能差；大多数消息系统和外部 API 不支持 XA。分布式数据库（Spanner、CockroachDB）内部的 2PC 之所以可行，是因为协调者和参与者都是通过 Raft / Paxos 复制的组，单台机器宕机不会让协调者消失，阻塞问题被共识化解了。
:::

::: details Saga 是怎么工作的？补偿操作要满足什么条件？
把大事务拆成一串本地事务 T1..Tn，每一步配一个补偿 C1..Cn。某一步失败时，按相反的顺序执行已完成步骤的补偿。补偿是语义上的撤销（退款、发更正通知），不是数据库回滚；补偿必须可以重试并且幂等。越过关键点（比如扣款）之后就不再回滚，而是一直向前重试直到完成。
:::

::: details Saga 缺少隔离性会带来什么问题？怎么缓解？
中间状态对外可见：库存已经扣了，但订单最后被取消了，期间别人看到的是一个从未真正生效的状态，可能因此做出错误的决定（比如提示库存不足）。缓解办法：语义锁（状态字段标记进行中）、设计可交换的更新、关键步骤前重新读取最新状态、用版本号防止覆盖。
:::

::: details TCC 和 Saga 有什么区别？TCC 有哪些经典的坑？
TCC 的 Try 阶段只预留资源（冻结），Confirm 时才真正生效，中间状态是「冻结」而不是「已经生效」，隔离性比 Saga 好；代价是每个服务都要实现 Try / Confirm / Cancel 三个接口，侵入性强。经典的坑：幂等（Confirm / Cancel 会被重试）、空回滚（没执行 Try 就收到 Cancel，要直接返回成功）、悬挂（Cancel 之后迟到的 Try 又冻结了资源，Try 前要检查事务是否已经取消）。都靠参与者维护的事务状态表解决。
:::

::: details LLMGateway 的预算是软上限。如果要改成硬上限，怎么设计？
用 TCC / 预留的思路：请求前按估算的 token 数原子地预留成本（Try，用 Lua 脚本检查并扣减），超出预算就拒绝；请求完成后按实际 usage 结算，多退少补（Confirm）；请求失败或超时时释放预留（Cancel），并给预留设置过期时间兜底。结算要幂等。代价是热路径上多一次 Redis 往返，这就是网关目前选择软上限的原因。
:::

::: details 编排式 Saga 和协调式 Saga 怎么选？
编排式没有中心，每个服务监听事件、执行、再发事件，耦合低，但流程和补偿链分散在各个服务里，难以看清和测试，适合步骤少的流程。协调式由一个协调者（工作流引擎）按步骤调用服务、失败时按顺序补偿，流程集中可见，便于处理超时和重试，步骤多或者补偿复杂时更合适。
:::

::: details agent 执行「订机票、酒店、租车」这种多步任务时，怎么保证失败时能回滚？
把它当作 Saga 来设计：每个预订是一个工具调用，同时提供对应的取消工具作为补偿，所有工具都要幂等。付款这种不可逆的关键步骤之前加人工审批。补偿链不要完全交给模型临场决定，而是写成确定性的工作流：模型负责选择方案，代码保证某一步失败后一定会按顺序执行补偿。
:::
