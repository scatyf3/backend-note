## 一句话结论

隐私工程的核心是三件事：==**少收集**（数据最小化）、**知道数据在哪**（数据地图）、**能按要求删干净**==。具体手段包括识别和分级 PII、最短保留期、最小的访问权限、传输和静态加密、脱敏和假名化、审计日志，以及支持用户的访问、删除、导出权利。LLM 应用多了三条数据外流的路径：

1. **发给模型供应商**：留存和训练政策、数据所在的区域；
2. **被复制到日志、trace、缓存、向量索引里**；
3. **被模型复述给其他用户**：通过 RAG、记忆或者缓存。

## 为什么隐私是一个工程问题

法规（GDPR、CCPA、HIPAA 等）给出的是原则和义务：合法的处理依据、数据最小化、用户可以要求删除、数据泄露要及时通报。落到系统上，就变成了一串工程问题：

- 这个字段是不是个人信息？谁能看到？存多久？
- 用户要求删除时，这份数据在多少个地方有副本？都能删掉吗？
- 数据有没有被发给第三方？对方会不会保留、会不会拿去训练？

这些问题，系统设计之初不考虑，事后几乎没法补救：数据已经被复制到了十几个地方。

## 什么是 PII

- **直接标识符**：姓名、邮箱、手机号、身份证号、精确的地址。
- **准标识符**：单独看不能识别一个人，组合起来就能。经典的研究发现，**邮编 + 出生日期 + 性别**就能唯一识别大约 87% 的美国人（Sweeney）。
- **敏感类别**：健康、财务、生物特征、宗教、性取向等，法规上有更严格的要求。
- **容易被忽略的**：IP 地址、设备 id、精确的位置、用户自己输入的自由文本（用户会在聊天框里粘贴任何东西）。

## 保护手段

### 最小化和保留期

最好的保护，是一开始就不收集。每个字段都要问一句：真的需要吗？需要存多久？给数据设置过期时间（TTL），到期自动删除。

### 加密

- **传输中**：全程 TLS（见[网络](/backend/network-tcp-http-tls)）。
- **静态**：磁盘加密是底线；更敏感的字段用**应用层加密**（数据库管理员和备份也看不到明文），通常用**信封加密**：每份数据一个数据密钥，数据密钥再由 KMS 里的主密钥加密。

### 假名化和匿名化

- **假名化**：用一个 token 或者 id 代替真实身份，但有办法还原（映射表、密钥）。按 GDPR，**假名化的数据仍然是个人数据**。
- **匿名化**：无法再关联回个人。真正的匿名化很难做到，准标识符的组合常常能重新识别出个人。
- **哈希不是匿名化**：邮箱做了 sha256，仍然可以对常见的邮箱列表算一遍哈希来反查（字典攻击）。需要「可比较但不可反查」时，用带密钥的 HMAC，并把密钥妥善保管。

### 访问控制和审计

最小权限：客服能看到订单，但看不到完整的卡号；工程师排查问题时，默认看到的是脱敏后的数据。所有对敏感数据的访问都要留下审计日志。

### 让删除真正生效

用户要求删除时，要删掉**所有副本**。这需要一张数据地图：

```
主库 → 只读副本 → 缓存 → 搜索 / 向量索引 → 日志 → trace → 分析仓库 → 备份 → 第三方
```

备份最难处理：总不能为了删一个用户去改每一份备份。一种做法是 **crypto-shredding**：每个用户的数据用一个独立的密钥加密，删除时直接销毁这个密钥，所有副本（包括备份）里这个用户的数据就都无法解密了。

## 实战：两个仓库的数据流

### 删除一篇文档，能删干净吗

DocPilot 删除文档时：

- `chunks` 表上有 `ON DELETE CASCADE`，chunk 连同它的向量和 `tsvector` 一起被删除，**向量索引和全文索引里也就没有了**；
- `traces` 表里只存了 chunk 的 id，查看时按 id 关联原文，所以 trace 里**不会残留原文**（见 [LLM tracing](/ai/llm-tracing)）。

但还有删不到的地方：

- **历史回答**：`messages` 表里存着模型过去的回答，回答里可能直接引用了这篇文档的原文。删除文档并不会改动这些回答。
- **网关缓存**：如果通过 LLMGateway 调用，exact cache 和语义缓存里存着完整的响应，要等 TTL（配置是 1 小时）过期才会消失。
- **模型供应商**：发送给供应商的 prompt 里包含了检索到的原文，对方可能会按自己的政策保留一段时间（比如用于滥用监控）。需要看合同条款，以及是否签订了零数据留存之类的协议。

### embedding 也是个人数据

把文本变成向量，并不等于匿名化。研究表明，可以从 embedding 相当程度地**还原出原文**（Morris et al. 2023，vec2text）。所以向量索引要和原文一样对待：同样的访问控制，同样的删除流程（见 [Embedding 与向量索引](/ai/embedding-vector-index)）。

### 日志里不写原文

LLMGateway 的语义缓存命中日志只记录 prompt 的 **sha256 前缀**和相似度，不记录 prompt 原文：既能审计误命中，又不会把用户输入写进日志系统。DocPilot 的 trace 只存工具调用的一行摘要。==日志和 trace 是最容易被忽视的 PII 副本==：保留期长，访问的人多，还经常被导出到第三方的分析平台（见[可观测性](/backend/observability)）。

### 缓存可能在租户之间共享

LLMGateway 的 exact cache 的 key、语义缓存的命名空间里，都**没有包含 API key 或者租户 id**。exact cache 的风险较小：输入完全相同，输出本来就相同。语义缓存的风险更大：两个不同租户的应用，如果用了相同的 system prompt，一个租户的回答就可能因为「问题相似」而被返回给另一个租户。如果回答里有租户的数据，就构成了跨租户泄漏。多租户部署时，应该把租户标识加进命名空间（见 [Prompt caching 与语义缓存](/ai/prompt-semantic-cache)）。

## LLM 应用的隐私清单

1. **发给模型之前先脱敏**：用正则加 NER 模型（比如 Presidio）识别 PII，替换成占位符，拿到回答后再还原。代价是可能影响回答质量，识别也不会百分之百准确。
2. **选对供应商的配置**：确认 API 数据是否会被用于训练、保留多久、存在哪个区域；需要的话，签订零数据留存协议或者使用指定区域的部署。
3. **记忆和缓存按用户隔离**：长期记忆、语义缓存、RAG 检索都要带上用户或租户的过滤条件（见[会话与记忆](/ai/conversation-memory)）。
4. **trace 和日志最小化**：存 id 和摘要，不存原文；设置短的保留期。
5. **删除要覆盖所有副本**：包括向量索引、缓存、trace，以及历史回答里的引用。

## 追问

::: details 什么是准标识符？为什么去掉姓名和身份证号还不够？
准标识符单独看不能识别一个人，但组合起来可以。经典研究发现，邮编、出生日期、性别三项就能唯一识别约 87% 的美国人。所以只删除直接标识符的数据，仍然可能被重新识别，尤其是和其他公开数据关联之后。真正的匿名化需要泛化、扰动或者差分隐私这类技术。
:::

::: details 假名化和匿名化有什么区别？把邮箱做 sha256 算匿名化吗？
假名化是用 token 代替身份，但存在还原的办法，GDPR 下仍然算个人数据；匿名化是无法再关联回个人。邮箱做 sha256 不算匿名化：攻击者可以对常见的邮箱列表算哈希来反查。需要可比较但不可反查时，用带密钥的 HMAC，并保护好密钥。
:::

::: details 用户要求删除数据时，后端要处理哪些地方？备份怎么办？
主库、副本、缓存、搜索和向量索引、日志、trace、分析仓库、备份、第三方，都要处理，前提是有一张清楚的数据地图。备份可以用 crypto-shredding：每个用户的数据用独立的密钥加密，删除时销毁密钥，所有副本里的数据都无法再解密。另外，日志和缓存设置较短的保留期，到期自然消失。
:::

::: details 在 DocPilot 里删除一篇文档，哪些副本会被清理，哪些不会？
会被清理：chunk（级联删除，连同向量和全文索引）；trace 里只存 id，原文自然关联不到。不会被清理：`messages` 表里历史回答引用的原文；网关 exact 和语义缓存里的响应（要等 1 小时 TTL）；模型供应商那边按其政策保留的 prompt。要做到彻底删除，还需要处理历史回答，并让缓存支持按内容失效。
:::

::: details 为什么说 embedding 也是个人数据？
向量不是不可逆的。研究表明（vec2text），可以从 embedding 相当程度地还原出原文。所以向量索引要和原文一样对待：同样的访问控制、按用户隔离、跟随删除。不能以为「存的只是向量」就可以放松保护。
:::

::: details LLMGateway 的语义缓存在多租户部署下有什么隐私风险？怎么改？
命名空间由 alias、system prompt、历史轮次和参数组成，不包含 API key 或租户 id。两个租户用了相同的 system prompt，一个租户的回答就可能因为问题相似被返回给另一个租户，回答里如果有租户数据就是泄漏。改法：把租户标识加进命名空间，或者按租户分开存储缓存；exact cache 风险较低，但最好也按租户隔离。
:::

::: details 把用户数据发给 LLM 供应商之前，要考虑哪些事？
1. 数据最小化：只发回答问题所需的部分；
2. 脱敏：用正则和 NER 识别 PII 并替换成占位符，回答后还原；
3. 供应商条款：是否用于训练、保留多久、数据在哪个区域，必要时签零数据留存协议或用指定区域的部署；
4. 在 trace 和日志里不存原文；
5. 告知用户并取得必要的同意。
:::
