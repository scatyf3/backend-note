# {{ $frontmatter.title }}

## 一句话结论

复制的目的有三个：**高可用**（一台挂了还有别的）、**读扩展**（多个副本分摊读请求）、**就近访问**（副本放在离用户近的地方）。核心难题是==副本之间的一致性，和延迟、可用性之间的取舍==。三种拓扑：单主、多主、无主（quorum）。同步还是异步复制，决定了故障时会丢多少数据。**共识算法**（Raft / Paxos）让一组节点对「日志的顺序」达成一致，是自动选主和强一致元数据存储（etcd、ZooKeeper）的基础。CAP 说的是：**发生网络分区时**，只能在一致性和可用性之间二选一。

## 为什么复制会带来一致性问题

数据只有一份时，读到的一定是最新的。一旦有多份副本，写入要传播到所有副本就需要时间，而网络会延迟、会丢包、会分区，节点会宕机。于是在任何一个时刻，不同副本上的数据可能不一样。所有的复制方案，都是在回答「允许不一样到什么程度、不一样的时候怎么办」。

## 三种复制拓扑

### 单主（主从）

所有写入都发给主库（leader），主库把变更日志（PostgreSQL 的 WAL、MySQL 的 binlog）发给从库（follower）。读可以发给任意副本。

| 方式 | 写入什么时候算成功 | 主库宕机时 |
|---|---|---|
| 同步复制 | 从库也写入之后 | 不丢数据，但任何一个同步从库变慢都会拖慢所有写入 |
| **异步复制** | 主库写入就返回 | **可能丢掉最近的写入**：从库还没收到，主库就挂了 |
| 半同步 | 至少一个从库收到之后 | 折中，最常见 |

### 复制延迟带来的异常

异步复制下，从库总是落后主库一点。读从库就会看到「过去」：

- **读不到自己刚写的（read-your-writes）**：用户刚发了一条评论，刷新页面却看不到，因为这次读请求落到了一个还没同步的从库上。解决：用户刚写入之后的一段时间内，读请求走主库；或者记下这次写入的日志位置（LSN），只从已经追上这个位置的从库读。
- **时间倒流（monotonic reads）**：两次刷新落到了延迟不同的两个从库上，第二次看到的数据反而更旧。解决：同一个用户固定读同一个从库。
- **因果颠倒（consistent prefix）**：先看到回答，后看到问题。解决：有因果关系的写入落到同一个分区。

**AI 应用里的例子**：DocPilot 每一轮开始时，从数据库读出会话历史作为模型的上下文（见[会话与记忆](/ai/conversation-memory)）。如果为了扩展读能力把这个查询发给只读副本，用户连续快速发两条消息，第二轮读到的历史可能**还没有包含第一轮的问答**，模型就「忘了」刚才说过什么。同样，刚上传完文档就提问，检索落到落后的副本上，会搜不到新文档。==会话历史和刚写入的数据，都要从主库读，或者保证 read-your-writes==。

### 故障切换和脑裂

主库宕机后：检测（心跳超时）→ 选出新的主库（通常选数据最新的从库）→ 客户端和其他从库切换到新主库。难点在于：

- **超时设多长**：太短会因为一次网络抖动误切换，太长则不可用时间变长。
- **脑裂**：旧主库其实没死，只是网络断了，恢复后它还以为自己是主库，两个主库同时接受写入。解决：用 **fencing token**（每次选主分配一个递增的编号，存储层拒绝编号更小的写入）、STONITH（强制让旧主库下线），或者干脆依赖一个共识系统来决定谁是主库。
- **异步复制下切换会丢数据**：旧主库上还没同步出去的写入，在新主库上不存在。

### 多主

多个节点都能接受写入，常见于多个数据中心各有一个主库。问题是**写冲突**：两个用户在两个机房同时修改同一条记录。解决办法：

- **最后写入者胜（LWW）**：按时间戳保留最新的。简单，但**会静默地丢数据**，而且依赖时钟，机器之间的时钟偏差会让「最新」变得不可靠。
- **CRDT**：设计成可以自动合并的数据结构（计数器、集合、协同文本）。
- **交给应用合并**：保留冲突的多个版本，由业务逻辑或者用户来决定。

### 无主（quorum）

Dynamo 风格（Cassandra、Riak）：没有主库，客户端直接写 N 个副本中的 W 个，读的时候读 R 个，取版本最新的那个。

- **$R + W > N$** 时，读到的副本集合和写入的副本集合至少有一个交集，所以一定能读到最新的写入。常见的配置是 N=3、W=2、R=2。
- 调小 W 写得更快，调小 R 读得更快，代价是一致性变弱。
- 修复数据的机制：**读修复**（读的时候发现某个副本是旧的，顺便更新它）、**hinted handoff**（目标节点暂时不可用时，由别的节点代存，恢复后再转交）、**反熵**（后台用 Merkle 树比对并修复差异）。
- 注意：quorum 并不等于线性一致，并发写入、sloppy quorum、读修复失败等边界情况下仍然可能读到旧数据。

## 一致性模型

从强到弱：

- **线性一致（linearizability）**：整个系统表现得就像只有一份数据，一个写入一旦完成，之后所有的读都能看到它。最直观，代价最高（要协调）。
- **因果一致**：有因果关系的操作，所有人看到的顺序都一样；没有因果关系的操作，顺序可以不同。
- **最终一致**：只要不再有新的写入，所有副本最终会变得一样，期间可能读到任何旧值。

还有几个面向单个用户的「会话保证」：read-your-writes、单调读、单调写。很多业务并不需要全局的线性一致，满足这几个会话保证就够了。

## CAP 与 PACELC

**CAP** 常被误读成「三个里面选两个」。正确的理解是：==网络分区（P）是一定会发生的，分区发生时，只能在一致性（C）和可用性（A）之间二选一==：

- **选 C**：分区的少数一侧拒绝服务（返回错误或者超时），保证不返回过期或冲突的数据。比如 etcd、ZooKeeper，以及配置成强一致的数据库。
- **选 A**：每个节点都继续服务，接受数据暂时不一致，之后再合并。比如 Cassandra、DynamoDB 的默认配置。

**PACELC** 补充了没有分区的时候：即使网络正常，也要在**延迟（L）**和**一致性（C）**之间权衡，比如同步复制更一致，但更慢。

## 共识：Raft

共识算法让一组节点（通常 3 或 5 个）对一个**有序的日志**达成一致。所有节点按同样的顺序执行同样的日志，就得到同样的状态（复制状态机）。

**选主**：

- 时间被分成一个个 **term**（任期），每个任期至多一个 leader。
- follower 在一个**随机的**超时时间内没有收到 leader 的心跳，就变成 candidate，任期加一，请求其他节点投票。随机超时是为了避免多个节点同时参选、一直平票。
- 节点只投票给**日志至少和自己一样新**的 candidate。这条规则保证了选出来的 leader 一定拥有所有已经提交的日志。
- 拿到**多数票**的成为 leader。

**日志复制**：

- 所有写入都发给 leader，leader 追加到自己的日志，并发送给 follower。
- **多数节点**确认写入之后，这条日志就是「已提交的」，可以执行并返回给客户端。
- 少数节点慢或者挂了，不影响提交。

**为什么是 2f+1 个节点**：容忍 f 个节点故障，需要剩下的节点仍然构成多数。3 个节点容忍 1 个故障，5 个节点容忍 2 个。4 个节点也只能容忍 1 个故障（多数是 3），所以集群规模一般是奇数。

**代价**：每次写入至少一次多数派往返；跨地域部署时延迟高；只适合存放较小的、关键的数据（配置、元数据、锁、选主信息），而不是业务数据本身。Kubernetes 的所有状态存在 etcd 里，etcd 用的就是 Raft；CockroachDB、TiKV 则把数据分成很多范围，每个范围是一个独立的 Raft 组。

## 时钟

- **物理时钟不可靠**：NTP 同步之后，不同机器之间仍可能差几毫秒到几百毫秒，时钟还可能被回拨。所以不要用不同机器上的时间戳来决定事件的先后（这正是 LWW 的问题）。
- **逻辑时钟**：Lamport 时钟给出一个和因果关系一致的全序；向量时钟能判断两个事件是有先后，还是并发发生的。
- **Google Spanner 的 TrueTime**：用 GPS 和原子钟把时钟误差控制在一个有界的区间内，提交时等待这个误差区间过去，从而在全球范围实现外部一致性。

## 实战：两个仓库的复制假设

- **DocPilot**：单个 PostgreSQL（Neon / Supabase 托管），目前读写都在主库上，没有复制延迟的问题。一旦为了扩展读能力引入只读副本，会话历史的读取和「刚上传就检索」都要特别处理，见上面复制延迟那一节。
- **LLMGateway**：README 写着「每个容器一个 worker，所有共享状态都在 Redis 里，所以可以通过增加副本来横向扩展」。网关本身是无状态的，状态集中在 Redis。Redis 的主从复制是**异步的**，主库故障切换时，最近的一些写入可能丢失：几次限流计数、几笔预算扣减。对网关来说，这是可以接受的，因为限流和预算本来就设计成软上限。但如果用 Redis 存放必须精确的数据（比如账户余额），就不能接受了。

## 追问

::: details 同步复制和异步复制各有什么优缺点？
同步复制：从库确认后才算写入成功，主库宕机不丢数据，但任何一个同步从库变慢或宕机都会拖慢甚至阻塞所有写入。异步复制：主库写完就返回，延迟低，但主库宕机时还没同步出去的写入会丢失，读从库还会遇到复制延迟带来的异常。实践中常用半同步：至少一个从库确认就返回。
:::

::: details 读从库会遇到哪些一致性问题？怎么解决？
1. **读不到自己刚写的**：刚写入后一段时间读主库，或者按写入的 LSN 只从已追上的从库读；
2. **时间倒流**：同一个用户固定读同一个从库；
3. **因果颠倒**：有因果关系的写入放在同一个分区。

AI 应用里的典型例子：会话历史从落后的副本读取，模型会「忘记」刚才的一轮对话，所以历史要从主库读。
:::

::: details 什么是脑裂？怎么防止？
旧主库因为网络断开被判定为宕机，新主库被选出来，网络恢复后旧主库仍然以为自己是主库，两个主库同时接受写入，数据出现分叉。防止办法：fencing token（每次选主分配递增的编号，存储层拒绝编号更小的请求）、STONITH（强制让旧主库下线）、依赖共识系统（多数派才能选出 leader，少数一侧无法写入）。
:::

::: details CAP 定理的正确理解是什么？
不是「三个选两个」。网络分区在分布式系统里一定会发生，CAP 说的是**分区发生时**，只能在一致性和可用性之间选：要么让分区一侧拒绝服务以保证一致（etcd、ZooKeeper），要么继续服务、接受暂时不一致之后再合并（Cassandra）。PACELC 补充了没有分区时的权衡：延迟和一致性之间的取舍。
:::

::: details 无主复制里 R + W > N 意味着什么？它能保证线性一致吗？
N 个副本，写 W 个、读 R 个，R + W > N 时，读到的副本和写入的副本至少有一个交集，所以能读到最新的写入。比如 N=3、W=2、R=2。但它不等于线性一致：并发写入、sloppy quorum（写到了 N 个之外的临时节点）、读修复失败等边界情况下，仍然可能读到旧值。
:::

::: details Raft 是怎么选主和提交日志的？为什么集群通常是奇数个节点？
选主：follower 在随机超时内没收到心跳，就成为 candidate，任期加一并请求投票；节点只投给日志至少和自己一样新的 candidate；拿到多数票的成为 leader。提交：leader 把日志复制给 follower，多数节点确认后提交。

容忍 f 个故障需要 2f+1 个节点：3 个容忍 1 个，5 个容忍 2 个；4 个节点也只能容忍 1 个故障，多一个节点只增加了开销，所以通常用奇数。
:::

::: details 为什么最后写入者胜（LWW）有问题？
1. 它会静默地丢掉并发写入中的一方，用户的修改莫名其妙地消失；
2. 它依赖时间戳，而不同机器的时钟有偏差、可能回拨，「最后」并不可靠，一个时钟偏快的节点的写入会一直胜出。

需要保留所有修改的场景，应该用 CRDT 或者应用层的合并逻辑。
:::
