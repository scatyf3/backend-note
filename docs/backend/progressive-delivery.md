## 一句话结论

**部署**（代码到达生产环境）和**发布**（用户看到新的行为）是两件事，应该分开。渐进式发布的目标是控制爆炸半径：

- **金丝雀**：先给一小部分流量用新版本，盯住指标，没问题再逐步放量，有问题自动回滚；
- **蓝绿**：两套环境，一次性切换，回滚就是切回去；
- **feature flag**：新代码已经部署了，但新行为由运行时的开关控制，按用户、租户或比例打开；
- **影子流量**：把真实请求复制一份给新版本，只比较结果，不返回给用户。

==这些手段能起作用的前提是：有能和基线对比的指标，以及事先定义好的自动回滚条件==。对 LLM 应用来说，换模型、改 prompt 也是一次发布，同样要走灰度。

## 为什么要渐进

测试环境永远不等于生产环境：真实的流量分布、数据、并发、依赖的行为，只有在生产环境里才会出现。一次性把新版本推给所有人，出了问题就是 100% 的用户受影响；先给 1% 的用户，同样的问题只影响 1%，而且能在影响扩大之前发现并回滚。

## 几种发布策略

### 金丝雀发布

```
部署新版本 → 1% 流量 → 观察 15 分钟 → 10% → 观察 → 50% → 100%
                 ↘ 任何一步指标异常 → 自动回滚到 0%
```

- **和谁比**：金丝雀组的指标要和**同一时间段的基线组**比较，而不是和昨天比，这样才能排除流量的时段波动。
- **比什么**：RED 指标（错误率、延迟分布），加上关键的业务指标（转化率、下单成功率）。
- **自动化**：Argo Rollouts、Flagger、Spinnaker 的 Kayenta 都能按指标自动推进或回滚。人盯着看既慢又容易漏。
- **流量怎么分**：可以按请求随机分，也可以按用户的哈希分。后者让同一个用户始终落在同一个版本上，体验一致，也便于对比。

### 蓝绿部署

保持两套完整的环境：蓝（当前）和绿（新版本）。绿环境部署好、验证通过之后，在负载均衡上一次性把流量切过去；有问题就切回蓝。

- **优点**：切换和回滚都是瞬间完成的；新版本可以在接收真实流量之前充分验证。
- **代价**：两倍的资源；**数据库通常是共享的**，所以 schema 必须同时兼容两个版本（见 [容器、K8s 与 CI/CD](/backend/containers-cicd) 里的 expand / contract）；长连接和正在进行的请求需要排空。

### Feature flag

把「新行为是否生效」从部署里拿出来，变成运行时可以修改的配置：

```python
if flags.enabled("new_ranker", user_id=user.id):
    results = new_rank(candidates)
else:
    results = old_rank(candidates)
```

flag 的几种用途：

| 类型 | 用途 | 生命周期 |
|---|---|---|
| 发布开关 | 未完成的功能先合并、先部署，但不对用户开放 | 短：功能稳定后删除 |
| 实验开关 | A/B 实验分组 | 短：实验结束后删除 |
| 运维开关（kill switch） | 出问题时一键关掉某个功能或依赖 | 长期保留 |
| 权限开关 | 按套餐、按客户开放功能 | 长期保留 |

实践要点：

- **分桶要稳定**：按 `hash(flag_name + user_id) mod 100` 决定用户落在哪个桶里，同一个用户每次的结果一样，放量从 5% 到 20% 时，原来那 5% 的用户仍然在里面。
- **flag 服务不可用时要有默认值**：flag 的求值通常在本地内存里完成，配置定期从服务端拉取；拉不到就用安全的默认值，而不是让请求失败。
- **flag 是技术债**：发布开关和实验开关用完必须删除，否则代码里会堆满永远为真（或永远为假）的分支，测试的组合也会爆炸。

### 影子流量（dark launch）

把生产请求复制一份发给新版本，新版本的结果**只用来比较，不返回给用户**。适合验证性能和正确性，尤其是重写一个核心组件的时候。要注意：新版本的**副作用必须关掉**（不能真的扣款、发邮件、写数据库），而且会额外消耗一份资源。

## 回滚

- **回滚要快，而且要演练过**：回滚流程从来没有用过，真正需要时多半会失败。
- **代码可以回滚，数据不一定**：如果新版本已经写入了新格式的数据，或者执行了破坏性的迁移，回滚代码之后，旧代码可能读不懂新数据。这就是为什么迁移要 expand / contract，新数据格式要向后兼容。
- **有时向前修复比回滚更快**：问题已经定位、修复很小时，直接发一个修复版本。但不要把「向前修复」当成不准备回滚的理由。

## LLM 应用：模型和 prompt 也要灰度

对 LLM 应用来说，下面这些都是「发布」，而且风险往往比改代码更大，因为行为变化更难预测：

- 换一个模型，或者模型的小版本更新；
- 修改 system prompt 或工具描述；
- 调整检索策略（切分方式、top_k、是否 rerank）。

### 把它们放到开关后面

- **网关是天然的切换点**：LLMGateway 里，应用请求的是别名（`fast`、`smart`），具体用哪个模型由网关配置决定。修改一个别名的链，所有应用立刻切换，也能立刻改回来。目前它不支持按比例分流，一个自然的扩展是给别名的链加上权重：`fast` 的 5% 走新模型，95% 走旧模型，并在 trace 里记录走了哪一边（见 [LLM 网关](/ai/llm-gateway)）。
- **按请求覆盖配置**：DocPilot 的 `/chat` 和 `/search` 接受请求级别的 `retrieval.mode` 和 `reranker` 参数，全局默认值则来自 `RETRIEVAL_MODE` 和 `RERANKER` 环境变量。这本身就是一种 flag：可以对一部分请求打开 rerank，对比效果，而不必为此部署新版本。
- **kill switch**：agent 的某个工具出了问题（比如 `create_page` 在生成重复页面），能不能不发版就把它关掉？可以把「哪些工具可用」做成运行时配置。

### 怎么判断新模型或新 prompt 更好

- **先离线**：在固定的 eval 数据集上对比（见[离线 eval](/stack/ev-offline)）。
- **再影子**：用真实流量同时跑新旧两个版本，新版本的回答不返回给用户，事后用 LLM judge 成对比较。没有用户风险，只多花一份调用费用。
- **最后金丝雀或 A/B**：小比例真实流量，对比线上的质量信号（点赞、点踩、追问率、拒答率）、延迟和成本，确认没有退化再放量（见[线上回归与 A/B](/stack/ev-online)）。

==trace 里一定要记录这次请求用的是哪个模型、哪一版 prompt==，否则灰度期间出现的问题，没法归因到具体的版本（见 [Prompt 设计与版本管理](/ai/prompt-versioning)）。

## 追问

::: details 部署和发布有什么区别？为什么要分开？
部署是新代码到达生产环境，发布是用户看到新的行为。分开之后，可以先部署、在内部验证，再逐步对用户开放；出问题时关掉开关就能「撤回发布」，不需要重新部署。feature flag 和金丝雀都是在利用这种分离。
:::

::: details 金丝雀发布的流程是什么？应该怎么判断能不能继续放量？
先部署新版本，给一小部分流量（比如 1%），观察一段时间，指标正常就逐步放量到 10%、50%、100%，任何一步异常就自动回滚。判断标准：金丝雀组和同一时间段的基线组对比 RED 指标（错误率、延迟分布）和关键业务指标，差异超过事先定义的阈值就回滚。最好交给 Argo Rollouts、Flagger 这类工具自动执行。
:::

::: details 蓝绿部署和金丝雀发布各有什么优缺点？
蓝绿：两套完整环境，切换和回滚瞬间完成，新版本可以在接流量前充分验证；代价是两倍资源，共享的数据库必须同时兼容两个版本，所有用户同时切换，风险没有被分摊。金丝雀：逐步放量，问题只影响小部分用户，资源开销小；代价是发布时间更长，需要好的指标和自动化分析，新旧版本要能同时运行。
:::

::: details feature flag 怎么保证同一个用户每次看到的版本一致？
用稳定的哈希分桶：`hash(flag 名 + user_id) mod 100`，落在开启比例以内的用户就开启。同一个用户的哈希值不变，所以结果稳定；比例从 5% 提高到 20% 时，原来那 5% 的用户仍然在开启范围内。把 flag 名加进哈希，是为了让不同 flag 的分组相互独立。
:::

::: details feature flag 有什么代价？怎么管理？
flag 会变成技术债：代码里堆满分支，测试组合爆炸，过期的 flag 没人敢删。管理办法：区分类型，发布开关和实验开关设置过期时间、用完删除，运维开关和权限开关长期保留；flag 服务不可用时有安全的默认值；在本地内存里求值，避免每次请求都远程调用。
:::

::: details 已经执行了数据库迁移，发现新版本有问题，能直接回滚代码吗？
要看迁移是否向后兼容。如果遵循 expand / contract，只做了新增（加列、加表），旧代码可以安全地运行在新 schema 上，直接回滚代码即可。如果做了破坏性的变更（删列、改类型），或者新版本已经写入了旧代码读不懂的数据，回滚代码会导致旧代码出错，只能向前修复或者恢复数据。这正是迁移要拆成多步的原因。
:::

::: details 怎么安全地把 LLM 应用切换到一个新模型？
1. 离线：在固定的 eval 数据集上对比正确率、引用忠实度、拒答率、延迟和成本；
2. 影子：用真实流量同时跑新旧模型，新模型的回答不返回给用户，事后用 judge 成对比较；
3. 金丝雀：通过网关按比例把一小部分流量切到新模型，对比线上的质量信号；
4. 全程在 trace 里记录模型和 prompt 版本，异常时在网关上一键切回。
:::
