# {{ $frontmatter.title }}

## 一句话结论

依赖**一定**会出故障。韧性设计的目标不是消除故障，而是==限制故障的爆炸半径：别让一个慢的依赖拖垮整个服务，别让一次小故障放大成雪崩==。手段是一套组合拳：

- **超时**：每次调用都要有上限，并沿调用链传递截止时间；
- **重试**：只对可重试的错误，加退避和抖动，有预算，只在一层做；
- **熔断**：依赖持续失败时快速失败，给它恢复的时间；
- **限流**：保护自己，也保护下游；
- **隔离舱**：不同依赖用独立的资源池；
- **降级和削峰**：过载时返回缓存或简化的结果，主动拒绝一部分请求。

## 为什么一个慢依赖能拖垮整个服务

假设服务调用一个依赖，平时 50 毫秒返回。某天它变慢了，每次要 30 秒：

1. 每个请求占着一个线程、协程或连接 30 秒，而不是 50 毫秒；
2. 并发数 = 吞吐 × 延迟（Little's Law），同样的流量下，占用的资源变成原来的 600 倍；
3. 线程池或连接池被占满，**连不依赖这个服务的请求也开始排队**；
4. 上游等不到响应开始重试，流量进一步放大，依赖更慢……

==慢比挂更危险==：挂了会立刻报错，慢则会悄悄地耗尽资源。下面每一个模式，都在打断这条链上的某一环。

## 超时

- **每一次网络调用都必须有超时**，没有例外。很多客户端库的默认超时非常长，甚至没有超时。OpenAI 和 Anthropic 的 Python SDK 默认超时是 10 分钟，还会自动重试 2 次。
- **区分连接超时和读取超时**：连接超时应该很短（几百毫秒到一两秒），读取超时按依赖的 p99 来设。
- **截止时间（deadline）要沿调用链传递**：用户请求总共只有 2 秒，调用链上每一层都应该知道「还剩多少时间」，时间不够就不必再发起下游调用。gRPC 的 deadline 会自动随调用传播。
- **LLM 调用要分开限制首 token 和总时长**：一次正常的流式回答可能持续一分钟，但首 token 迟迟不来就说明出问题了。LLMGateway 的流式请求用 `timeout_s` 限制「等到第一个 chunk」的时间，超时就 fallback；首 token 之后不再受这个超时限制。

## 重试

规则见[幂等与错误语义](/backend/idempotency)：只重试可重试的错误（超时、5xx、429），操作必须幂等，指数退避加抖动，设置重试预算，**只在一层重试**。

一个实际的叠加例子：DocPilot 通过 OpenAI SDK 调用 LLMGateway，而 SDK 默认会对 429 / 5xx / 连接错误重试 2 次；网关内部又会沿着 fallback 链尝试多个后端。如果网关的整条链都失败，返回 502，SDK 会再从头来两遍，总尝试次数翻了三倍。网关自己把 Anthropic SDK 的 `max_retries` 设成了 0，就是为了避免这种叠加。但调用网关的客户端是否也这么做，网关管不了。所以它在预算耗尽时回 402（SDK 不会重试），而不是 429。

## 熔断器

### 状态机

```
        失败率超过阈值              冷却时间到
CLOSED ───────────────→ OPEN ───────────────→ HALF-OPEN
  ↑                      ↑                       │
  │                      └──── 探测失败 ──────────┤
  └────────────── 探测成功 ───────────────────────┘
```

- **CLOSED（闭合）**：正常放行，统计一个时间窗口内的失败率和慢调用率。
- **OPEN（断开）**：失败率超过阈值后，**直接快速失败**，根本不去调用依赖。上游立刻拿到错误（可以马上降级），依赖也得到了喘息的时间。
- **HALF-OPEN（半开）**：冷却一段时间后，放少量探测请求过去，成功就恢复 CLOSED，失败就回到 OPEN。

熔断器要**按依赖的实例**来维护（每个后端、每个下游服务各一个）。Envoy 的 outlier detection、resilience4j 都是现成的实现。

### 实战：LLMGateway 缺一个熔断器

LLMGateway 的 router 按别名配置的固定顺序依次尝试后端，失败了才 fallback 到下一个。后端是否「可用」（`Backend.available`）只取决于有没有配置凭证，是一个**静态**属性，router 并不知道后端最近的健康状况。

设想 Anthropic 不是返回 5xx，而是**卡住不响应**：

- 每一个 `fast` 请求都会先尝试 Anthropic，等满 `timeout_s`（配置是 60 秒）超时，才 fallback 到 OpenAI；
- 故障期间，**所有**请求都多花 60 秒，p99 直接爆掉；被占住的协程和连接越来越多，网关自己也可能被拖垮。

加上熔断器之后：连续几次超时，Anthropic 的熔断器打开，后面的请求直接跳到 OpenAI，延迟只多了一次判断；冷却时间到了再放一个探测请求，确认 Anthropic 恢复后再切回来。==fallback 解决的是「失败了怎么办」，熔断解决的是「明知道会失败，就别再去试了」==，两者需要配合使用。

## 限流

### 算法

| 算法 | 原理 | 特点 |
|---|---|---|
| 固定窗口 | 每个时间窗口一个计数器 | 简单；**窗口边界可能放过 2 倍流量**（上个窗口最后一秒和下个窗口第一秒各打满） |
| 滑动窗口日志 | 记录每个请求的时间戳 | 精确，但内存随请求量增长 |
| 滑动窗口计数 | 当前窗口和上一个窗口按比例加权 | 近似值，内存小 |
| **令牌桶** | 桶按固定速率补充令牌，请求消耗令牌，最多攒满容量 | **允许突发**（攒满时），长期速率受控；最常用 |
| 漏桶 | 请求进队列，以固定速率流出 | 输出非常平滑，不允许突发 |

LLMGateway 的 `limits.py` 开头就写了为什么选令牌桶而不是固定窗口：固定窗口会让客户端在窗口边界发出 2 倍于限额的请求，而令牌桶连续补充、允许最多一个容量的突发。

### 分布式限流

网关有多个副本时，限流状态必须共享，通常放在 Redis 里。关键是**检查和扣减必须是原子的**，否则两个副本会同时读到「还剩 1 个」然后都放行。LLMGateway 的做法：

- 一个 Lua 脚本同时处理 RPM 和 TPM **两个桶**：先检查所有桶都够，再统一扣减。只要有一个桶不够，就都不扣，返回 429 和 `Retry-After`（根据令牌补充速率算出要等多久）。
- 输出 token 在请求时未知，响应结束后再用另一个脚本补扣（post-paid），**允许桶变成负数**，下一个请求自然要等到「欠款」被补回来。
- 一个可以改进的细节：脚本里用的当前时间是**调用它的网关副本传进去的**。多个副本之间如果有时钟偏差，令牌的补充量就会算错。改用 Redis 服务器自己的时间（脚本里调用 `TIME`），所有副本看到的就是同一个时钟（时钟问题见[复制与一致性](/backend/replication-consensus)）。

### 在哪里限流

- **边缘 / 网关**：按 API key、用户、IP 限流，保护自己不被单个客户端打垮；
- **按租户**：防止一个大客户挤占其他人；
- **对下游**：保护一个有限额的依赖（LLM 供应商的 RPM / TPM），在自己这一侧排队，而不是等着被对方 429。

## 隔离舱（bulkhead）

船体分成多个密封舱，一个舱进水不会沉船。对应到服务：**给不同的依赖分配独立的资源池**（线程池、连接池、并发信号量），某个依赖变慢，只会耗尽它自己的池子。

例如：LLM 调用很慢，一次几十秒；数据库查询很快，几毫秒。如果两者共用同一个线程池或者同一个并发上限，LLM 一慢，数据库查询也跟着排队。DocPilot 跑在单个 asyncio 事件循环上，协程本身很便宜，但数据库连接池（`max_size=10`）是有限的。要注意不要在持有数据库连接的时候去等 LLM 调用。DocPilot 的写法是检索完立即归还连接，然后才调用模型，这是对的。

## 削峰与降级

- **主动拒绝（load shedding）**：过载时尽早拒绝一部分请求（返回 503），而不是让所有请求都变慢、最后一起超时。依据可以是队列长度、在途请求数、延迟；被拒绝的优先是低优先级的流量。更进一步是**自适应并发限制**：根据观测到的延迟动态调整允许的在途请求数。
- **降级**：依赖不可用时，返回一个「足够好」的结果：
  - 返回缓存里的旧数据；
  - 换一个更小、更便宜的模型；
  - 跳过一个可选的步骤。

一个 DocPilot 里的例子：rerank 是可选的增强步骤，但 `CohereReranker` 在 Cohere 返回错误时会直接抛异常（`raise_for_status`）。这个异常会让整个 `search_docs` 工具失败，模型拿到的是一条错误，而不是检索结果。更合理的做法是捕获 rerank 的错误，**退回到 RRF 融合后的顺序**，并在 trace 里记一笔。==可选的步骤失败，不应该让主功能失败==。

## 追问

::: details 为什么说一个慢的依赖比一个挂掉的依赖更危险？
挂掉的依赖会立刻返回错误，资源马上释放。慢的依赖会让每个请求长时间占着线程、连接或协程，按 Little's Law，同样的流量下占用的资源成倍增加，很快耗尽线程池或连接池，连不相关的请求也开始排队；上游超时重试又进一步放大流量。所以每次调用都要有超时，再配合熔断和隔离舱。
:::

::: details 超时应该怎么设置？什么是 deadline 传播？
每次网络调用都必须有超时；连接超时设得短，读取超时参考依赖的 p99。deadline 传播：用户请求有一个总的截止时间，调用链上的每一层都知道还剩多少时间，时间不够就不再发起下游调用，避免做无用功。gRPC 会自动传播 deadline。LLM 调用要分别限制首 token 时间和总时长。
:::

::: details 熔断器的三个状态是什么？它和 fallback 有什么区别？
CLOSED：正常放行并统计失败率；OPEN：失败率超过阈值后直接快速失败，不调用依赖；HALF-OPEN：冷却后放少量探测请求，成功就恢复，失败就回到 OPEN。fallback 解决「这次失败了怎么办」，熔断解决「明知道会失败就别去试」。LLMGateway 只有 fallback 没有熔断，主后端卡住时，每个请求都要先等满 60 秒超时才会 fallback。
:::

::: details 令牌桶和固定窗口限流有什么区别？
固定窗口每个时间窗口一个计数器，简单，但在窗口边界可能放过 2 倍的流量。令牌桶按固定速率补充令牌、最多攒到容量，请求消耗令牌：允许最多一个容量的突发，长期速率受控，没有边界问题。漏桶则以固定速率输出，最平滑但不允许突发。LLMGateway 选择令牌桶，原因就写在 `limits.py` 的注释里。
:::

::: details 多个网关副本共享限流状态时，怎么保证不超发？
把状态放在 Redis，并且让「检查」和「扣减」原子地完成，用一个 Lua 脚本在 Redis 内部执行，否则两个副本会同时读到「还剩 1 个」然后都放行。LLMGateway 在一个脚本里同时检查 RPM 和 TPM 两个桶，都够才一起扣减。另外，最好用 Redis 服务器的时间（`TIME`）计算令牌补充量，避免各副本时钟偏差带来的误差。
:::

::: details 什么是隔离舱模式？举一个例子。
给不同的依赖分配独立的资源池（线程池、连接池、信号量），一个依赖变慢只会耗尽它自己的池子。例子：LLM 调用一次几十秒，数据库查询几毫秒，如果共用一个并发上限，LLM 一慢数据库查询也要排队。还要注意不要在持有数据库连接时等待 LLM 调用，那样会把慢依赖的延迟传导到连接池上。
:::

::: details 一个可选的增强步骤（比如 rerank）调用失败了，应该怎么处理？
降级而不是失败：捕获错误，退回到没有这一步时的结果（RRF 融合后的顺序），在 trace 和指标里记一笔，必要时对这个依赖打开熔断。DocPilot 当前的实现里，Cohere 出错会让整个 search_docs 工具失败，模型拿到的是一条错误，属于可以改进的地方。原则是可选的步骤失败，不应该让主功能失败。
:::
