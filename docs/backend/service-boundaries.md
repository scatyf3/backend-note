# {{ $frontmatter.title }}

## 一句话结论

单体还是微服务，本质上不是技术选择，而是**组织和演进**的选择。微服务用独立部署、独立扩展、故障隔离和团队自治，换来了分布式系统的全部复杂度：网络调用、部分失败、跨服务的数据一致性、运维和调试的成本。==默认从模块化单体开始==，按业务能力划分清楚的模块边界；等团队规模、发布节奏、扩展需求、硬件需求真的分化了，再把模块拆成服务。判断一个服务边界合不合理，标准只有两条：**能不能独立部署**，以及**是否独占自己的数据**。

## 为什么不是越拆越好

一个函数调用变成一次网络调用，会带来一连串新问题：

- **延迟**：纳秒级的函数调用变成毫秒级的网络往返，一个请求串了 10 个服务，延迟就叠加 10 次；
- **部分失败**：被调用方可能超时、出错，甚至「处理了但响应丢了」，每一个调用点都要考虑重试、幂等、超时、熔断（见[限流、熔断与重试](/backend/rate-limit-circuit-breaker)）；
- **数据一致性**：原来一个本地事务能搞定的事，现在要用 Saga、Outbox（见[分布式事务](/backend/distributed-transactions)）；
- **运维**：每个服务都要有自己的部署流水线、监控、告警、日志；
- **调试**：一个问题要跨多个服务追踪（见[可观测性](/backend/observability)）；
- **接口演进**：服务之间的 API 变成了契约，改动要考虑兼容性（见 [API 设计](/backend/api-design)）。

这些成本是实实在在的，只有当拆分带来的收益超过它们时，拆分才划算。

## 单体和微服务的取舍

| | 单体 | 微服务 |
|---|---|---|
| 部署 | 一次部署全部，简单；但任何改动都要整体发布 | 各自独立部署；但要协调版本和兼容性 |
| 扩展 | 只能整体扩容 | 按服务分别扩容，资源利用更好 |
| 调用 | 进程内函数调用，快，不会部分失败 | 网络调用，慢，会部分失败 |
| 一致性 | 本地事务 | Saga、最终一致 |
| 团队 | 小团队效率高；团队大了容易互相阻塞 | 团队可以自治，各自负责自己的服务 |
| 故障隔离 | 一个模块的内存泄漏能拖垮整个进程 | 一个服务挂了，其他服务可以降级继续运行 |
| 技术栈 | 统一 | 可以各自选择 |

**康威定律**：系统的结构往往会映射组织的沟通结构。微服务的核心收益之一是让团队能够独立交付，所以它更多地是解决一个**组织规模**的问题。几个人的团队拆出十几个服务，通常是在给自己制造麻烦。

### 最坏的情况：分布式单体

拆成了多个服务，却：

- 每次发布都要几个服务一起部署（服务之间耦合太紧）；
- 多个服务直接读写**同一个数据库**的同一批表；
- 服务之间同步调用链很长，一个服务慢，所有服务都慢。

这样就同时承受了单体的耦合和微服务的复杂度，两头的缺点都占全了。

## 怎么划分边界

- **按业务能力，而不是按技术分层**：「订单」「支付」「库存」是好的边界；「数据访问层服务」「工具类服务」不是。领域驱动设计（DDD）里的**限界上下文**就是用来找这种边界的：在一个上下文内部，概念的含义是一致的。
- **高内聚、低耦合**：经常一起改动的东西放在一起；一个用户请求如果总要来回调用三四个服务，说明边界可能划错了（接口太「健谈」）。
- **每个服务独占自己的数据**：别的服务只能通过它的 API 访问它的数据，不能直接读它的表。这是能独立部署、独立演进的前提。
- **同步还是异步**：需要立即得到结果的用同步调用（REST、gRPC）；通知类的、可以晚点处理的用事件（见 [Outbox 与事件驱动](/backend/outbox-event-driven)）。

### 模块化单体

一个可部署单元，但内部按业务划分成边界清楚的模块：每个模块对外只暴露明确的接口，模块之间不直接访问彼此的内部实现和数据表。好处是：

- 保留单体的简单（一次部署、本地事务、进程内调用）；
- 边界清楚，**将来真的需要时，拆出去的成本很低**。

### 什么时候真的该拆

- **扩展特征不同**：一个模块需要 GPU，另一个只需要 CPU；一个要扩到 100 个实例，另一个 2 个就够。
- **发布节奏不同**：一个模块每天发布好几次，另一个几个月才改一次。
- **团队边界**：一个团队需要独立负责、独立交付。
- **安全或可靠性要求不同**：比如支付模块要更严格的隔离和审计，或者某个模块持有高价值的密钥。

迁移的经典方式是**绞杀者模式**（strangler fig）：在原系统前面放一个路由层，把一个个功能逐步迁移到新服务，路由逐步切过去，直到旧系统可以下线，而不是一次性重写。

## 实战：两个仓库的边界选择

### DocPilot：一个模块化单体

DocPilot 的后端是一个 FastAPI 应用，内部按职责分成边界清楚的模块：`ingest/`（解析、切分、入库）、`retrieval/`（检索、融合、重排）、`agent/`（循环、工具、提示词、引用）、`llm/`（各家供应商的适配器）、`routes/`（HTTP 接口），共享一个 Postgres。前端（Next.js）是一个独立部署的单元，部署在 Vercel，后端在 Fly。

这个选择是合理的：

- 所有数据在一个 Postgres 里，入库可以用一个本地事务完成，不存在双写（见 [Outbox 与事件驱动](/backend/outbox-event-driven)）；
- eval 可以在进程内直接调用同一个 app；
- 模块之间的接口是清楚的（比如 `Toolbox` 接收的是几个普通的 async 函数，`LLMProvider` 是一个 Protocol），将来要拆，比如把入库拆成独立的 worker（见[后台任务](/backend/background-jobs)），改动量很小。

### LLMGateway：为什么单独成一个服务

网关是一个独立部署的服务，而不是 DocPilot 里的一个模块。理由正好对应上面「什么时候该拆」的几条：

- **服务多个应用**：限流、预算、缓存、计量这些能力，是所有调用 LLM 的应用都需要的，放在某一个应用里就没法复用；
- **安全边界**：供应商的 API key 只放在网关上，应用拿到的是网关签发、只存哈希的 key（见[认证与鉴权](/backend/auth)）；
- **扩展特征不同**：网关本身无状态，状态全在 Redis，可以独立地水平扩展；
- **边界是一个标准协议**：DocPilot 通过 OpenAI 兼容的 HTTP 接口调用网关，只要改一个 `OPENAI_BASE_URL`，也可以不经过网关、直接调用供应商，耦合非常松。

### 自托管的模型：硬件决定边界

LLMGateway 的 `deploy/vllm-slurm.sh` 在大学集群的一张 GPU 上启动 vLLM，网关再把 `local` 和 `cheap` 这两个别名路由过去。模型推理需要 GPU，和普通的 CPU 应用完全是两种资源、两种运维方式（这里甚至是两种调度系统：Slurm 和容器平台），**硬件差异是最自然的服务边界**（见[自托管推理还是调 API](/stack/ai-selfhost)）。

## AI 系统里常见的边界

- **模型推理**：需要 GPU，单独部署、单独扩展；
- **LLM 网关**：横跨所有应用的平台服务；
- **检索服务**：多个应用共享同一个知识库时，可以独立出来；只有一个应用使用时，留在应用里更简单；
- **agent 的运行时**：长时间运行的 agent 需要 durable execution，适合单独的 worker 池（见[长任务与 human-in-the-loop](/stack/ag-durable)）；
- **eval 和数据处理**：离线任务，按批次运行。

划边界的时候也要想到数据一致性：比如向量和原文放在同一个数据库里，入库就是一个本地事务；拆成独立的向量服务，就要处理双写。

## 追问

::: details 单体和微服务各有什么优缺点？
单体：部署简单、进程内调用快、有本地事务、重构容易；但改动要整体发布，只能整体扩容，团队大了容易互相阻塞。微服务：独立部署和扩展、故障隔离、团队自治；但要承担网络延迟、部分失败、跨服务一致性、运维和调试的成本，还有接口兼容性的约束。它主要解决的是组织规模的问题。
:::

::: details 什么是「分布式单体」？怎么识别？
拆成了多个服务，但仍然紧密耦合：每次发布都要几个服务一起部署，多个服务共享同一个数据库的表，同步调用链很长、一个服务慢全部都慢。它同时承受了单体的耦合和微服务的复杂度。识别信号：无法独立部署某个服务、改一个功能要动好几个服务、服务直接读别人的表。
:::

::: details 应该怎么划分服务边界？
按业务能力（限界上下文）划分，而不是按技术分层；高内聚低耦合，经常一起改动的放在一起，一个请求需要频繁来回调用多个服务说明边界划错了；每个服务独占自己的数据，别人只能通过 API 访问；需要立即结果的用同步调用，通知类的用事件。
:::

::: details 什么是模块化单体？为什么推荐从它开始？
一个部署单元，但内部按业务划分成边界清楚的模块，模块之间只通过明确的接口交互，不直接访问彼此的内部实现和数据。它保留了单体的简单（一次部署、本地事务、进程内调用），又让边界保持清晰，将来真的需要时拆出去的成本很低。DocPilot 的后端就是这样组织的。
:::

::: details 什么情况下应该把一个模块拆成独立的服务？
扩展特征不同（一个需要 GPU 或大量实例，另一个不需要）；发布节奏差异很大；需要一个独立的团队负责和交付；安全或可靠性要求不同（比如持有高价值的密钥）；被多个应用复用。LLMGateway 单独成服务，就是因为它服务多个应用、持有供应商的密钥、独立扩展。
:::

::: details 怎么把一个单体逐步迁移到微服务？
用绞杀者模式：在原系统前面放一个路由层，把一个个功能迁移到新服务，路由逐步切换过去，直到旧系统可以下线，而不是一次性重写。迁移时先拆边界最清楚、收益最明显的模块，数据也要一起迁移，让新服务独占自己的数据，避免变成分布式单体。
:::

::: details 一个 AI 应用里，哪些部分适合拆成独立的服务？
模型推理（需要 GPU，硬件不同是最自然的边界）；LLM 网关（横跨所有应用的平台能力，也是密钥的安全边界）；多个应用共享知识库时的检索服务；长时间运行的 agent 运行时；离线的 eval 和数据处理任务。只被一个应用使用、和应用数据强一致的部分（比如向量和原文）留在一起更简单。
:::
