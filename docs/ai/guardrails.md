# {{ $frontmatter.title }}

## 一句话结论

guardrails 是包在模型调用两侧的检查：

- **输入侧**：越狱和注入检测、PII 脱敏、话题范围、长度和频率限制；
- **输出侧**：结构校验、事实和引用校验、敏感内容过滤、策略合规；
- **执行侧**：工具调用的参数和权限校验。

==能用规则判断的就不用模型，能用小模型判断的就不用大模型==；要权衡关键路径上的延迟（并行执行、流式检测）；每一道检查失败之后怎么办（拒绝、改写、重试、转人工）要事先设计好。guardrails 自己也会误报，也需要 eval。

## 为什么需要 guardrails

模型的行为没法完全保证（见[采样、非确定性与幻觉](/ai/sampling-nondeterminism)）：它可能被注入、可能编造、可能输出不该输出的内容，也可能输出格式不对的结果。prompt 里写的「不要做什么」只是请求，不是保证。guardrails 是**模型之外**的代码，在模型的输入和输出上强制执行规则。它和 [Agent 权限与沙箱](/stack/sec-sandbox)一起，构成纵深防御：权限限制「最坏能做什么」，guardrails 尽量在问题发生前拦下它。

## 三个位置

```
用户输入 ──[输入 guardrails]──→ 模型 ──[输出 guardrails]──→ 用户
                                  │
                                  └─ 工具调用 ──[执行 guardrails]──→ 工具
```

| 位置 | 检查什么 | 例子 |
|---|---|---|
| 输入 | 请求是否合法、是否在服务范围内、是否包含攻击或敏感数据 | 长度上限、越狱检测、PII 脱敏、话题分类 |
| 输出 | 回答是否格式正确、有依据、安全、合规 | JSON schema 校验、引用校验、内容审核、去除 PII |
| 执行 | 工具调用是否合法、是否在权限内、是否需要审批 | 参数校验、权限检查、高风险操作拦截 |

## 三种实现方式

| 方式 | 例子 | 延迟和成本 | 准确性 |
|---|---|---|---|
| **规则** | 正则匹配 PII、长度限制、JSON schema、域名白名单、关键词列表 | 几乎为零 | 确定，但只能覆盖能写成规则的情况 |
| **分类模型** | 供应商的内容审核接口、专门的安全分类模型（比如 Llama Guard）、注入检测模型 | 低，几十毫秒 | 覆盖面广，有误报和漏报 |
| **LLM 判断** | 用一个模型判断回答是否被资料支持、是否违反某条政策 | 高：一次额外的模型调用 | 最灵活，但最贵、最慢，自身也可能出错 |

按这个顺序组合：先用规则拦下明确的情况，规则管不了的再交给分类模型，只有确实需要理解语义的才动用 LLM。

## 实战：盘点两个仓库已有的 guardrails

DocPilot 没有一个叫「guardrails」的模块，但它已经有好几道这样的检查：

**输入侧**

- 问题为空返回 422；请求体用 pydantic 模型校验；
- 上传文件限制类型（扩展名白名单）和大小（20 MB，虽然检查时机偏晚，见 [OWASP](/backend/owasp)）。

**执行侧**

- 工具参数用 pydantic 严格校验：`extra="forbid"`、`top_k` 在 1 到 10 之间、标题长度上限；
- 不存在的工具、不合法的 JSON 都会转成错误结果回传给模型，不会被执行（见 [Tool calling 与 MCP](/ai/tool-calling-mcp)）；
- **被截断的 tool call 不执行**：`stop_reason` 为 `max_tokens` 时，循环直接结束这一轮（见 [Agent 循环](/stack/ag-loop)）。

**输出侧**

- **引用校验**：回答里的 `[c:id]` 回数据库查询，查不到的 id 不会变成引用；
- **拒答检测**：固定的拒答句，用代码确定性地识别；
- **模型的拒绝**：供应商返回 `refusal` 时，循环补一句说明，并把 `finish_reason` 标记为 `content-filter`。

LLMGateway 则在网关层提供了另一组：按 key 限流和预算、按等级限制可用的模型、明确拒绝 assistant prefill 这类不支持的请求、语义缓存的严格阈值。

这次盘点说明：==很多最有效的 guardrails 就是普通的输入校验和输出校验==，不一定需要专门的框架。缺少的主要是内容层面的检查，比如输入的注入检测、输出的敏感内容过滤和 PII 脱敏。

## 和流式输出的冲突

输出侧的检查通常需要看到完整的回答，但流式输出时，token 在生成的同时就已经发给了用户。几种处理办法：

1. **事后附加**：DocPilot 的引用校验在生成结束后进行，结果作为 `data-citations` 事件追加在流的末尾。它只是**补充**信息（把引用变成可以点击的按钮），不需要撤回已经显示的文字，所以和流式输出天然兼容。
2. **按句或按块检查**：缓冲一小段（比如一句话），检查通过后再发出。延迟增加有限，能拦住大部分问题。
3. **事后撤回**：先流式输出，检查不通过时在界面上把这段回答替换成提示。用户可能已经看到了内容，只适合风险不高的场景。
4. **先检查再输出**：高风险的场景放弃流式，生成完整的回答、检查通过后再一次性返回。

## 检查失败之后怎么办

| 动作 | 适用场景 |
|---|---|
| 拒绝，返回一个说明 | 越狱、明显违规的请求 |
| 改写或脱敏后放行 | 输出里有 PII、多余的格式 |
| 带着错误信息让模型重试 | 结构校验失败（JSON 不合法、缺字段），通常重试一次就能修好 |
| 退回安全的模板回答 | 检查服务不可用，或者多次重试都失败 |
| 转人工 | 高风险领域（医疗、金融建议），或者用户明确要求 |

每一次拦截都要记录下来，并且定期抽查，判断是真的拦对了，还是误伤。

## guardrails 自己也要评估

- **误报**：正常的请求被拦下，用户体验很差，而且常常没人发现。比如一个过严的注入检测，会把所有提到「忽略之前的设置」的正常问题都拦掉。
- **漏报**：真正的攻击没拦住。
- 评估方法：准备一组正常请求和一组对抗样本，分别统计拦截率；上线后持续监控各道检查的触发率，突然升高或降低都值得查看（见[线上评估](/stack/ev-online)）。

## 放在哪一层

- **网关层**：适合与业务无关的通用检查，比如限流、预算、通用的内容审核、PII 脱敏。所有应用统一受益。
- **应用层**：适合依赖业务语境的检查，比如引用校验、话题范围、工具权限。只有应用自己知道「这个回答应该基于哪些文档」。

## 追问

::: details guardrails 分别可以放在哪几个位置？各检查什么？
输入侧：请求是否合法、是否在服务范围内、是否包含越狱或注入、是否有需要脱敏的 PII。输出侧：格式是否正确、是否有依据（引用校验）、是否包含敏感或违规内容。执行侧：工具调用的参数是否合法、是否在用户权限内、是否需要人工审批。
:::

::: details 规则、分类模型、LLM 判断三种 guardrails 怎么选？
按成本和能力递进组合：规则（正则、schema、白名单）几乎零成本、结果确定，先用规则拦下能明确描述的情况；分类模型（内容审核接口、Llama Guard）覆盖面更广，延迟低，但有误报和漏报；LLM 判断最灵活，可以理解语义，但贵、慢，自身也会出错，只用在确实需要理解语义的检查上。
:::

::: details 流式输出和输出侧 guardrails 有什么冲突？怎么处理？
输出检查通常要看完整的回答，但流式输出时 token 已经先发给了用户。处理方法：只做补充性质的检查，在流末尾附加结果（DocPilot 的引用校验）；按句缓冲，检查通过再发出；先输出再撤回（适合低风险）；高风险场景放弃流式，检查完再整体返回。
:::

::: details DocPilot 已经有哪些 guardrails？还缺什么？
输入侧：空问题返回 422、请求体 pydantic 校验、上传类型和大小限制。执行侧：工具参数严格校验、不存在的工具和非法 JSON 转为错误结果、被截断的 tool call 不执行。输出侧：引用回库校验、确定性的拒答检测、供应商拒绝时的处理。缺的主要是内容层面的检查：输入的注入检测、输出的敏感内容过滤和 PII 脱敏。
:::

::: details 一道输出检查不通过，应该怎么处理？
按情况选择：明显违规就拒绝并说明；有 PII 或多余内容就脱敏改写后放行；结构不合法就带着错误信息让模型重试，一般一次就能修好；检查服务挂了或者多次失败就退回安全的模板回答；高风险领域转人工。每次拦截都要记录，定期抽查是否误伤。
:::

::: details 为什么说 guardrails 本身也需要评估？
guardrails 会误报，也会漏报。误报会拦下正常请求，体验很差而且常常没人发现；漏报则形同虚设。要准备正常请求和对抗样本两组数据，分别统计拦截率；上线后持续监控各道检查的触发率，突然变化就要查看原因。
:::

::: details 哪些 guardrails 适合放在网关，哪些必须放在应用里？
和业务无关的通用检查适合放在网关：限流、预算、通用的内容审核、PII 脱敏，所有应用统一受益。依赖业务语境的检查必须放在应用里：引用校验（只有应用知道回答应该基于哪些文档）、话题范围、工具权限。
:::
