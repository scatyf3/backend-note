# {{ $frontmatter.title }}

## 一句话结论

离线 eval 只能覆盖**你想到的**问题，线上评估看的是**真实发生的**问题。线上质量信号有四类：

- **隐式信号**：重新生成、追问、复制、放弃、会话长度；
- **显式反馈**：点赞、点踩、文字评论；
- **自动化的线上打分**：对采样的 trace 跑规则检查和 judge；
- **业务指标**。

要比较两个版本谁更好，就做 **A/B 实验**：==随机分组，事先定好主指标和护栏指标，算好需要的样本量，不要中途偷看结果就下结论==。LLM 场景的特殊之处在于方差大、单个质量信号噪声大，而成本和延迟本身就是必须守住的护栏。

## 为什么离线 eval 不够

- **分布不同**：离线数据集是你构造的，真实用户的问题更杂、更短、更口语化，还会问你从没想到的东西。
- **会漂移**：用户的问题会变；文档库在更新；供应商的模型也可能在你不知情的情况下更新。离线数据集是静态的，跟不上这些变化。
- **只有线上才有的维度**：用户是否满意、是否完成了任务、是否愿意继续用，离线根本测不出来。

所以离线 eval 和线上评估是一个闭环：线上发现问题 → 加进离线数据集 → 修复后离线验证 → 再上线观察。

## 线上质量信号

### 用户的信号

| 信号 | 可能的含义 | 陷阱 |
|---|---|---|
| 点赞 / 点踩 | 直接的满意度 | **非常稀疏**，只有少数用户会点；点的人有偏差（不满意的人更愿意点） |
| 重新生成 | 对这个回答不满意 | 也可能只是想看另一个版本 |
| 紧接着追问 | 回答不完整或不清楚 | 也可能是用户感兴趣、想深入 |
| 复制回答 | 回答有用 | 也可能是复制下来去别处验证 |
| 会话中途放弃 | 体验不好 | 也可能是已经得到了答案 |

隐式信号量大但含义模糊，显式反馈含义清楚但量少。实践中两者结合，并且看**趋势和相对变化**，而不是绝对值。

### 自动化的线上检查

对线上 trace（全量或采样）跑**确定性的规则**，不需要人，也不需要 judge。拿 DocPilot 现有的代码就能算出好几个有用的指标：

- **幻觉引用率**：回答里 `[c:id]` 标记的数量，减去回库校验后真正解析出来的引用数。查不到的 id 就是模型编出来的（见[采样、非确定性与幻觉](/ai/sampling-nondeterminism)）。
- **拒答率**：`is_refusal` 判定为拒答的比例，突然升高通常意味着检索出了问题，或者 prompt 改得太严。
- **截断率**：`finish_reason` 为 `length` 的比例。
- **步数耗尽率**：`finish_reason` 为 `other` 的比例，说明 agent 用完 6 步还想继续调用工具。
- **工具错误率**：trace 的工具日志里 `is_error` 为真的比例，按工具分别统计。
- **延迟和成本的分布**：直接来自 trace。

在这之上，再对一小部分采样的 trace **异步**地跑 LLM judge。比如引用忠实度：trace 里有检索到的 chunk id，可以还原出被引用的原文，交给 judge 判断（见[离线 eval](/ai/offline-evals)）。异步、采样，是为了不影响线上延迟，也控制 judge 的成本。

### 漂移监控

给上面这些指标设置基线和告警，重点盯住**突变**：

- **问题分布的漂移**：新的话题、新的语言（DocPilot 碰到中文问题时，全文检索那一路会悄悄失效）；
- **语料的变化**：文档大量更新或删除之后，检索质量可能变化；
- **供应商模型的变化**：拒答率、输出长度、延迟突然变了，而你这边什么都没改，很可能是供应商更新了模型。所以要尽量使用固定的模型版本，并在 trace 里记录。

## A/B 实验

### 基本设计

1. **假设**：比如「打开 rerank 会提高回答质量，延迟增加不超过 300 毫秒」。
2. **随机化单位**：按**用户**（或者会话）分组，而不是按请求。同一个用户在两个版本之间来回切换，体验不一致，而且同一次对话的前后轮次会互相影响。用稳定的哈希分桶（见[灰度与 feature flag](/backend/progressive-delivery)）。
3. **主指标**：一个最能代表成功的指标，比如「没有重新生成、也没有点踩的回答占比」。
4. **护栏指标**：不能变差的指标，比如 p95 延迟、每次对话的成本、错误率、拒答率。主指标变好但护栏被突破，也不能上线。
5. **样本量**：根据基线水平、想检测到的最小提升（MDE）、显著性水平和统计功效，**事先**算好需要多少样本、要跑多久。时长至少覆盖一个完整的周期（比如一周），以排除工作日和周末的差异。

### 常见的错误

- **偷看**：每天看结果，一显著就停。这样会大大增加假阳性的概率。要么跑满事先定好的样本量，要么使用专门为持续观察设计的序贯检验方法。
- **样本比例失配（SRM）**：设计的是 50 / 50，实际是 52 / 48，说明分组过程本身有 bug（比如某个版本更容易出错，导致日志丢失），这时实验结果不可信。
- **新奇效应**：用户一开始对新东西特别感兴趣，指标虚高，过一段时间回落。
- **只看平均值**：整体持平，可能是某一类问题变好、另一类变坏，要分群查看。

### 检索策略的实验：interleaving

比较两种检索或排序策略时，A/B 往往需要很大的样本量。**interleaving** 更灵敏：对同一个查询，把两种策略的结果交错合并成一个列表展示给用户，看用户更多地点击（或者模型更多地引用）来自哪一方的结果。因为是在同一个查询上直接对比，消除了用户之间的差异。对 RAG 来说，可以统计「最终被引用的 chunk 来自哪种检索策略」。

### LLM 场景的特殊之处

- **方差大**：同样的输入输出也不同，用户的反馈又稀疏，需要更大的样本。
- **成本是一等的护栏**：一个更好但贵三倍的方案，未必值得上线。
- **线上 judge 也有偏差**：用 judge 打分作为实验指标时，两组用同一个 judge，比较的是相对差异。
- **离线和线上要互相印证**：如果离线 eval 显示变好，线上却没变化甚至变差，说明离线数据集和真实分布脱节了，要回头改进数据集。

## DocPilot 可以从哪里开始

1. **加反馈**：每条回答下面加点赞和点踩，存进一张表，用 `message_id` 关联到 trace。
2. **先算确定性的指标**：幻觉引用率、拒答率、截断率、步数耗尽率、工具错误率。这些都能从现有的 trace 和回答里直接算出来，不需要额外的模型调用。
3. **利用现成的实验开关**：`/chat` 已经支持请求级别的 `retrieval.mode` 和 `reranker` 覆盖。按用户哈希分组，一组打开 rerank、一组不开，对比主指标和延迟护栏。
4. **闭环**：每周把被点踩的、幻觉引用的、步数耗尽的回答捞出来，人工看一遍，挑出有代表性的（去掉个人信息）加进离线数据集。

## 追问

::: details 已经有了离线 eval，为什么还需要线上评估？
离线数据集是人构造的、静态的，和真实流量的分布不同，覆盖不到没想到的问题；用户的问题、文档库、供应商的模型都会变化；用户满意度、任务完成度只有线上才能测。线上发现的问题要回流到离线数据集，形成闭环。
:::

::: details 点赞点踩和重新生成、追问这些隐式信号，各有什么优缺点？
显式反馈含义清楚，但非常稀疏，而且有选择偏差，不满意的人更愿意点。隐式信号量大，但含义模糊：追问可能是不满意，也可能是感兴趣；复制可能是有用，也可能是要去别处验证。实践中两者结合，看趋势和相对变化，并用来挑选需要人工查看的样本。
:::

::: details 不调用任何模型，能从线上 trace 里算出哪些质量指标？
以 DocPilot 为例：幻觉引用率（回答里的引用标记数减去回库校验成功的引用数）、拒答率、截断率（`finish_reason` 为 length）、步数耗尽率（finish_reason 为 other）、按工具统计的错误率、延迟和成本的分布。这些确定性的指标可以全量计算并设置告警，再对一小部分采样跑异步的 judge。
:::

::: details A/B 实验应该按请求分组还是按用户分组？为什么？
通常按用户（或者会话）分组。按请求分组时，同一个用户会在两个版本之间来回切换，体验不一致；对话的前后轮次也会互相影响，破坏了组间的独立性。用 `hash(实验名 + user_id)` 做稳定分桶。
:::

::: details 设计一个 LLM 功能的 A/B 实验，要定哪些指标？
一个主指标（最能代表成功的，比如没有被重新生成、也没被点踩的回答占比），加上一组护栏指标：p95 延迟、每次对话的成本、错误率、拒答率。主指标变好但护栏被突破，也不能上线。所有指标、需要的样本量和实验时长都要事先确定。
:::

::: details 做 A/B 实验时，为什么不能每天看结果、一显著就停？还有哪些常见的错误？
反复查看、一显著就停，会大大增加假阳性的概率：随机波动总有某一天会越过显著性阈值。要么跑满事先算好的样本量，要么使用为持续观察设计的序贯检验。其他常见错误：样本比例失配（分组本身有 bug）、新奇效应、只看平均值不分群、时长太短没有覆盖完整的周期。
:::

::: details 比较两种检索策略，除了 A/B 还有什么更灵敏的方法？
interleaving：对同一个查询，把两种策略的结果交错合并成一个列表，看用户更多地点击、或者模型更多地引用来自哪一方的结果。因为是在同一个查询上直接对比，消除了用户和查询之间的差异，需要的样本量比 A/B 小得多。RAG 里可以统计最终被引用的 chunk 来自哪种策略。
:::
