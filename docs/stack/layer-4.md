# 第 4 层：异步与编排

这一层回答「怎么把事情拆出请求路径，并且保证它最终做完」。它建立在第 2 层的状态之上（任务、事件、进度都要持久化），又为第 5 层的分布式一致性提供素材（Saga 就是一种编排）。左边是传统后端的四件套，从简单到可靠依次是：消息队列（解耦生产和消费）、后台任务（把慢活交给 worker）、Outbox（让「写数据库」和「发事件」不再二选一地丢失）、工作流和 durable execution（把多步流程的进度持久化，崩溃后从断点继续）。右边是 agent：**agent 循环本质上就是一个长时间运行、每一步都由模型决定下一步的编排**，它天然继承了左边所有的老问题：每一步可能失败、要能重试、要幂等、要有步数和时间上限、进度要能持久化。长任务和 human-in-the-loop 则需要把 agent 的执行从一次 HTTP 请求里解放出来，交给 durable execution 来托管。

- **消息队列**：队列模型和日志模型，at-least-once 加幂等，顺序只在分区内保证。
- **后台任务**：任务队列、重试、超时、可见性，以及 Postgres `SKIP LOCKED` 这种轻量方案。
- **Outbox 与事件驱动**：用本地事务同时写业务数据和待发事件，解决双写问题。
- **工作流与 durable execution**：把流程状态持久化，Temporal 一类的引擎怎么保证「做完」。
- **Agent 循环**：模型调用 → 执行工具 → 回传结果，停止条件、步数上限、并行工具调用。
- **长任务与 human-in-the-loop**：跑几小时的 agent、等待人工审批时怎么挂起和恢复。
